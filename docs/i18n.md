# Internationalization

The interface ships in English and Mexican Spanish. Both are first-class: the
Spanish is not a machine translation of the English, and the editorial AI
prompts are written separately in each language rather than translated.

Stack: [next-intl](https://next-intl.dev) v4, configured in `i18n/`.

| File | Purpose |
|---|---|
| `i18n/routing.ts` | Locales, default locale, and the URL prefix strategy |
| `i18n/request.ts` | Loads the message bundle for the resolved locale |
| `i18n/navigation.ts` | Locale-aware `Link`, `redirect`, `useRouter`, `usePathname` |
| `messages/en.json` · `messages/es.json` | The strings |
| `i18n/STYLE_GUIDE.md` | Tone and terminology, per locale |

## URLs

`localePrefix: "as-needed"`: English is unprefixed (`/dashboard`), Spanish is
prefixed (`/es/dashboard`). The proxy (`proxy.ts` — Next.js 16 exports
middleware as `proxy`) resolves the locale, then strips the prefix before the
auth checks, so route protection is written against canonical paths.

## The parity rule

`messages/en.json` and `messages/es.json` must have **identical key sets**. A
test enforces it, and CI fails on a mismatch. This is the single most common
reason a PR goes red.

Add a key to one file, add it to the other in the same commit. If your Spanish
is shaky, say so in the PR — a rough translation flagged as rough is welcome; a
confident wrong one is not.

## Writing strings

```tsx
// Server component
import { getTranslations } from "next-intl/server";
const t = await getTranslations("dashboard");

// Client component
import { useTranslations } from "next-intl";
const t = useTranslations("dashboard");

<h1>{t("title")}</h1>
```

Rules worth internalising:

- **Never concatenate translated fragments.** Word order differs. Use one key
  with placeholders: `t("greeting", { name })`, not `t("hello") + name`.
- **Plurals go through ICU**, not an `if`:
  `"chapters": "{count, plural, =0 {No chapters} one {# chapter} other {# chapters}}"`.
- **Keys describe the place, not the text.** `settings.ai.keyStatus.set`
  survives a copy change; `settings.ai.keyIsSet` does not.
- **Numbers, currency, and dates go through the formatter.** `useFormatter()`,
  or the `formatCurrency` / `formatDate` helpers in `lib/utils.ts` — es-MX peso
  and date conventions are handled there. Never hand-build a currency string.

## Common mistakes

- `useRouter`, `usePathname`, and `redirect` must come from
  `@/i18n/navigation`, not `next/navigation`, or the locale is lost on
  navigation. The server-side `redirect` takes `{ href, locale }` and its
  return value must be returned explicitly.
- The routing locale is `es`, not `es-MX`; URLs stay `/es`. The `es-MX`
  conventions are applied by the formatter, not by the route segment.
- Metadata (titles, descriptions, hreflang) is localized too — see `lib/seo.ts`.

## Adding a locale

Genuinely wanted; Brazilian Portuguese is the obvious next one. Please open an
issue to claim a language first, because these are large PRs and duplicated
effort is painful.

1. Add the locale to `i18n/routing.ts`.
2. Copy `messages/en.json` to `messages/<locale>.json` and translate it. Keep
   the key set identical, and extend `tests/unit/i18n-parity.test.ts` to cover
   the new file — today it compares `en` and `es` by name.
3. Add the language to `components/marketing/LanguageSwitcher.tsx`.
4. Add a section to `i18n/STYLE_GUIDE.md`: how formal to be, what to call a
   *manuscript*, a *chapter*, a *royalty*. Consistency in the domain vocabulary
   matters more than elegance in any single string.
5. If you want the editorial AI to work in that language, the prompts in
   `lib/ai/prompts/` need a version written by someone who writes fiction in it.
   The interface can ship without this; say so in the PR if you are skipping it.

Translation is maintenance, not a one-off. Say in the issue whether you are
willing to keep the locale current — that is what decides whether it ships.
